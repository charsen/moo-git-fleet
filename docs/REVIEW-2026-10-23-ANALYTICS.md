## 一、复盘

### 1. 这一轮做了什么

从「数据是不是每次都全量算」开始，最后落成五件事：

| # | 事项 | 结果 |
|---|---|---|
| 1 | 性能：主 log 缓存 + numstat 增量对账 | 稳态 127ms → 77ms；fetch 后那次 3.0s → 0.07s |
| 2 | 非上班时长口径复核 | 1,362.6h → 1,276.3h（−6.3%）；午休单列、准备时间只在重开时补 |
| 3 | 文案精审 22 处 | 最大发现：同屏并存「近 52 周」与「全部历史」两种口径 |
| 4 | 时间段筛选（默认近一年） | 整页统一口径；13/26/52/104 周四档 |
| 5 | 条形视觉：两端对齐 → 交界缝隙 → 压暗红 | 三轮，见下 |

### 2. 唯一真正的返工：同一个交界处改了三次

| 轮次 | 我的判断 | 实际原因 | 代价 |
|---|---|---|---|
| 第一轮 | 「条两端与文字的盒边界差 1.5px」 | 判断正确但不是用户说的那处 | 1 次打包安装 |
| 第二轮 | 「两个 flex 子元素各自栅格化，接缝会漂」 | 结构上确实该改，但仍不是成因 | 1 次打包安装 |
| 第三轮 | 逐像素还原截图，发现几何完全对齐 | **马赫带**：绿 169 / 红 108 亮度差 60，硬边被视觉放大 | 1 次打包安装 + 一次改色 |

三次里有两次改的是几何，而问题从来不在几何。**根因是我一直在用「几何证据」回答一个
「知觉问题」**：headless 截图能量出像素，量不出眼睛看到的东西。

### 3. 复盘出的四条

1. **先分清「几何缺陷」和「知觉缺陷」**。用户说「错位/不齐」时，先量像素；量出来是齐的，
   就立刻转向对比度与明度差（马赫带、同时对比），而不是继续调 0.5px。第三次终于做对，
   是因为把用户截图逐像素还原了，而不是又渲染一张自己的截图。
2. **同一处被报两次，第二次就该停下来问，而不是再猜一版**。第二次我确实问了，但问题问得
   太技术（「是上下沿不齐还是中间有缝」），用户只能用「台阶」这种词回答，反而把方向带回几何。
   更好的问法是给图：左边原样、右边试改，让他指哪一个。
3. **结构性改动要一次到位**。把一个 10px 的条从「两个矩形」改成「一条渐变」是对的，但当时
   没有顺手解决「两种高对比纯色直接相接」这个更上游的问题。如果第一次就把「两块颜色要不要
   接触」一起想清楚，可以少一轮。
4. **每一轮都补了断言，这是唯一没有白付的代价**：`verify:ui` 从 194 项涨到 234 项，
   其中「删除段比新增段暗」「图例色块与条同色」「交界处有一条透明缝」「界面提交数与接口一致」
   都是这几轮返工沉淀下来的，现在改回旧行为会立刻红。

### 4. 做得好的地方

- 窗口定义只有一个出处（`shared/report-window.ts`），服务端算完把 `range` 回传，客户端照着画，
  两边不可能差一周；
- 缓存按「引用签名 / 窗口起点」分项失效，并在注释里写清了每一项为什么这样失效；
- 非上班时长的常量与分母用单测绑定（`normalWorkday = 480`），口径改动会立刻暴露；
- 「标签跟数据走、不跟按钮走」这个决定避免了一次典型的假象（「近两年 · 数字与近一年相同」）。

## 二、业务代码审核

按影响排序。每条都给了证据（文件:行）与建议改法。

### P1｜活跃度卡在窄窗口下会丢仓库（本轮引入的潜在回归）

**证据**：`server/analytics/heatmap.ts:553`

```ts
if (windowed.total === 0) continue;   // 窗口内没有提交 → 不进 byRepo
```

客户端 `client/components/CommitHeatmap.vue:251` 用 `byRepo` 分桶：

```ts
const freshness = computed(() => bucketRepositoryFreshness(props.data?.byRepo ?? [], new Date()));
```

**影响**：选「近 3 个月」时，90 天没动过的仓库窗口内 0 提交 → 被 `continue` 跳过 →
「91 天以上」那一档变少甚至归零。卡片标题是「最近一次提交距今」，它天然是全历史问题，
不该跟着窗口缩水。

**为什么现在看不出来**：本机 22 个仓库在 13 周内都有提交，实测 13/26/52/104 四档 `byRepo`
都是 22 条、分桶都是 `≤7:7 / 8–30:12 / 31–90:3 / >90:0`。只要有一个仓库闲置 90 天以上就会显形。

**建议**：`byRepo` 保留所有「有历史提交」的仓库（窗口内 `total` 允许为 0），
排行侧用 `total > 0` 过滤，活跃度卡直接吃全量。或者新增 `repositories[]` 只带
`{id, name, lastCommitDate}` 给活跃度卡，语义更清楚。

### P1｜轮询失败会把整页打成错误态，尽管数据还在

**证据**：`client/App.vue:263` + `client/components/CommitHeatmap.vue:513`

```ts
const heatmapError = computed(() => { const error = heatmapQuery.error.value; if (!error) return null; ... });
```
```html
<div v-else-if="error" class="heatmap-state heatmap-error">
```

**影响**：`refetchInterval: 60_000` 每分钟重取一次；任意一次失败（后端忙、git 超时）都会让
`error` 有值，而错误分支排在数据分支之前——整页从图表变成「分析数据加载失败」，直到下一次
成功。`placeholderData` 保住了 data，但模板不给它机会。

**建议**：`error && !data` 才进错误态；有数据时把错误降级成一行提示（可带「重试」），
下次成功自动消失。

---

### P2｜窗口放宽要重算 2.8–3.0 秒（收窄只要 0.15 秒）

**证据**：`server/analytics/heatmap.ts:385` 起的 `readCodeVolume`；`code-volume.ts:172`
的 `reconcileCommitVolumes` 会按 `listed` 裁剪基线。

实测（23 仓库）：

```
52 → 152ms   13 → 135ms   52 → 2765ms   13 → 147ms   104 → 2990ms   52 → 150ms
```

收窄不花时间（全是命中），放宽要重新 diff 几千个提交——因为收窄那一步把基线裁掉了。

**建议**：给 `CommitCodeVolume` 加一个 `authorDate` 字段，基线只增不减（存并集），
聚合时在内存里按窗口过滤。这样只要历史上扫过一次最宽的窗口，之后任何切换都是零 git 调用；
`--since` 只在「基线里没有更早的数据」时才跑。

---

### P2｜代码量按 committer date 划界，其余指标按 author date

**证据**：
- `heatmap.ts`：`rev-list ... --since=<windowStart>` 与 `git log ... --since=<windowStart>`
  ——`--since` 走的是 **committer date**；
- `parseLog` 用 `%aI`（**author date**）分日、分小时、算非上班时长。

**影响**：rebase / cherry-pick 会让两者分叉。一笔 2025-10 写的提交在 2026-09 被 rebase 进来，
它会进「近一年代码量」，但热力图把它画在 2025-10 那一周（窗口外，不显示）；反过来，
窗口最早那几天会有「热力图有格子但代码量没算」的提交。量级不大，但窗口边界上必然出现，
而且用户已经在同一屏里对比这两个数。

**建议**：numstat 的输出里加 `%aI`，聚合时按 author date 过滤（与热力图同口径）。
`--since` 仍然保留，用来把 diff 的量降下来，只是不再作为最终判据。

---

### P2｜并发请求不去重

**证据**：`server/analytics/heatmap.ts` 的 `aggregateCommitHeatmap` 每次调用都从头跑一轮。

**影响**：60 秒轮询 + 手动刷新 + 开着两个窗口时，同一批 `git log` 会并发跑。
缓存能兜住「结果」，兜不住「同时进行的重复扫描」。

**建议**：以 `窗口周数 + 仓库集合 + 引用签名` 为 key 缓存 in-flight promise，
同一时刻只跑一次，其余请求 await 同一个结果。

---

### P3｜「统计中…」每分钟闪一次

**证据**：`client/App.vue:5606`

```html
:refreshing="heatmapQuery.isFetching.value && !heatmapQuery.isLoading.value"
```

`isFetching` 包含 60 秒一次的后台轮询，于是工具栏每分钟闪一次「统计中…」。

**建议**：只在真正换了范围时显示——`data.range.weeks !== weeks`；轮询用一个更弱的提示
（或干脆不提示）。

---

### P3｜作者别名会随窗口变

**证据**：`heatmap.ts` 聚合时只用窗口内的作者样本喂 `resolveAuthors`（`author-identity.ts`）。

**影响**：同一个人的另一种写法（`charsen` / `charsen fung`）如果只出现在窗口外，
窄窗口下就归并不上，排行里可能拆成两行、`含别名` 也会少一个。

**建议**：身份归并用全历史样本（缓存里已经有），只是提交数按窗口累加。

---

### P3｜缓存内存上限只算了提交时间

**证据**：`heatmap.ts` 的 `maxCachedMinutes` 用 `log.minutes.length` 计数；
超限时 `resetAnalyticsCache()` **整体清空**。

按天存的 `days`（每天 24 个计数 + 作者 map）没有计入，一个十年每天提交的仓库可以撑到
几百 KB 而不被计数；一旦触发又是全清 + 下一请求全量重扫。

**建议**：把 `days.size` 也折算进去；淘汰改成逐条 LRU，而不是整体清空。

### P3｜服务端静默回落，界面不提示

`?weeks=abc` 回落到 52 已经写进注释与测试，但客户端拿到 `range.weeks !== 所选 weeks` 时
没有任何提示。不影响正确性，属于「出错也看不出来」的一类。

---

### P3｜「涉及 N 天」把 1 分钟的日子也算进去

`overtime.ts` 的 `activeDays` 是「当天非上班时长 > 0 的天数」。实测 796 天里有 46 天

这个数字会被更频繁地读到。

## 六、第二轮复盘与优化（2026-10-23 傍晚）

这一轮的口径：**先用数据确认问题存在，再改**。没有实测支撑的「优化」一律不动。

### 1. 一次真实事故，暴露了界面在替 git 猜原因

装完 0.1.45 后，分析页显示 53 个仓库全部「读取失败」，提示是
「目录不可访问或不是 Git 仓库，请到『仓库舰队』检查路径」。

真实原因完全不是这个：

```
You have not agreed to the Xcode license agreements.
Please run 'sudo xcodebuild -license' from within a Terminal window ...
```

本机 `xcode-select -p` 指向 `/Applications/Xcode.app/Contents/Developer`，而 Xcode 许可未接受，
`/usr/bin/git` 这个 shim 直接拒绝执行。**所有 git 命令都跑不了，和仓库路径一点关系都没有。**

服务端其实拿到了 stderr，但 `readRepositoryDaily` 用 `.catch(() => null)` 把它吞了，
只回一个 `unreadable: { count, names }`，界面只能硬编码一个猜测。猜错的代价是
用户去翻一堆没问题的路径。

**改法**：`RepositoryScan` 加 `reason`，把 git 的 stderr 第一行（截断到 200 字）带回契约；
`summary.unreadable` 增加 `reason`，多个仓库同因失败时按出现次数取最常见的一条（Map 保序，并列取先遇到的）。
空仓库**不带**原因——它的 `git log` 也会失败（`ambiguous argument 'HEAD'`），
把那句话显示出来只会让人以为仓库坏了。

改完实测（故意在 git 不可用的环境里起服务）：

```json
{ "count": 53, "names": ["charsen-com", ...], "reason": "You have not agreed to the Xcode license agreements. ..." }
```

界面上那句话直接换成 git 的原话。**这是本轮唯一一处真正的 bug 修复**，其余都是确认无问题。

### 2. 性能：先量，再决定要不要动

53 个真实仓库，`/api/analytics/heatmap`：

| 场景 | 并发 6（现状） | 并发 12 | 结论 |
|---|---|---|---|
| 冷启动（首屏） | 4.11 s | 3.69 s | 只快 10%，瓶颈是单个大仓库的 numstat，不在并发数 |
| 暖缓存（轮询） | 0.110 s | 0.083 s | 快 27%，但每次只省 27 ms，肉眼不可见 |

并发没有调：本机 14 核，翻倍并发换 10% 冷启动，代价是瞬时进程数翻倍——
一个后台工作台在用户正用电脑时突然起 12 个 git，不值。**保持 6。**

暖缓存的 110 ms 几乎全是「每个仓库一次 `git rev-parse` 算引用签名」：
53 次进程启动 ÷ 6 并发 × ~12 ms ≈ 110 ms。这是缓存正确性的代价，不打算省。

真正的冷启动大头是 `git log --numstat`。想再快只能改架构（两阶段接口或落盘缓存），
属于另一个量级的改动，本轮不做，理由见第 5 节。

|---|---|---|
| 冷启动改两阶段接口（热力图先回、代码量后到） | 首屏 4.1 s → 约 0.3 s | 会打破刚统一的「整页一个口径」——两个响应到达时间不同，卡片会先空后跳。要做就得同时设计骨架态与「仍在统计」标记，是功能级改动 |
| numstat 结果落盘缓存 | 二次启动接近 0 成本 | 需要缓存格式、失效条件、损坏降级三件事，且和现有的内存基线要能共存。风险大于收益 |
| 热力图格子的键盘可达性 | 读屏与键盘用户 | 364 个格子逐个 `tabindex` 反而更糟，正确做法是一组 roving tabindex + 方向键，属于交互设计，不该顺手塞进优化轮 |
